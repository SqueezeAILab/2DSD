# Training

2DSD trains two components:

- **Shared-KV adaptation** (`training.kd`, Appendix C): adapt Ouro and Nanbeige to last-loop KV sharing
  with a local window of W = 64 through self-distillation from the original model.
- **Depth-conditioned drafters** (`training.drafter`, Appendix D.4): train and export DFlash drafters
  for the shared-KV and original targets. Dory uses one drafter for both targets and needs no KD.

Run commands from the repository root after [installation](../README.md).
Use model names from [configs/models.json](../configs/models.json); `--model-path` and `--target-path`
accept local checkpoints or Hugging Face repo IDs.

## Shared-KV adaptation (KD)

The [KD configs](../configs/kd) use 32K document-isolated sequences and a 128M input-token budget.
The student first computes detached last-loop KV with a per-loop KV forward, then applies the shared rule
in a second pass. The loss is full-vocabulary forward KL from the frozen original model, averaged over
response tokens. Optimizer and schedule settings are in the configs.

```bash
torchrun --standalone --nproc-per-node 4 -m training.kd.train \
    --config configs/kd/ouro-1.4b-w64.json --data DATA_DIR --out runs/kd/ouro-1.4b-w64
```

To resume, repeat the command with `--resume runs/kd/ouro-1.4b-w64/last`, using the same config,
data and world size. Use `--model-path` to supply the original checkpoint, `--max-updates` and
`--skip-evaluation` for a short run, and `--checkpoint-layers` / `--activation-offload` to control
activation memory.

Checkpoints under `RUN/checkpoint-<tokens>/model` contain the model and tokenizer. Their config enables
shared-KV inference through this repository's vLLM fork. The Transformers model forward computes
per-loop KV.

Evaluate a checkpoint:

```bash
python -m training.kd.evaluate --model ouro-1.4b-thinking --checkpoint RUN/last/model --data DATA_DIR \
    --window 64 --exact --out dev-kl.json
```

### Training data

The paper uses OpenThoughts3-1.2M conversations. The training data is not included in this release;
prepare data in one of the following layouts.

**Ouro: token arrays**

```text
DATA_DIR/
  ready.json                       data_ready, data_hashes for train/dev
  manifest.json                    optional record_index with document domains
  tokenized/{train,dev}/
    tokens.npy                     concatenated prompt + response token IDs
    offsets.npy                    document boundaries, from 0 to len(tokens)
    loss_mask.npy                  contiguous response suffix through EOS per document
    meta.json
```

`meta.json` contains `ordered_record_ids`, `tokens`, `target_tokens`, `template_kwargs`,
`model_revision` matching the registry, and `files` mapping array filenames to SHA256 hashes.
It also contains `data_hash_payload`, its digest as `data_hash` (matching `ready.json`), and tokenizer
asset hashes under `tokenizer_fingerprint_payload.asset_sha256`.

**Nanbeige: JSONL documents**

```text
DATA_DIR/
  {train,dev}.jsonl                 id, input_ids, prompt_length, domain
  {train,dev}.index.json            byte offsets, input_tokens, targets
  {train,dev}.packs.json            document indices, input_tokens, targets per pack
  manifest.json                    model_tokenizer, sequence_length, seed, file hashes
```

The response starts at `prompt_length` and ends at EOS. Packing preserves whole documents and isolates
attention between them. Prepare Nanbeige data with its native chat template:

```bash
python -m training.kd.prepare_nanbeige --parent D_OT3_MESSAGES --out DATA_DIR_NANBEIGE
```

The parent directory contains `manifest.json` with shard hashes, ordered record IDs per split and
Nanbeige tokenizer hashes under `config.tokenizers`; `ready.json` with `data_ready` and
`manifest_sha256`; and `shards/*.jsonl.gz` rows with `record_id`, `messages`, `prompt_history_sha256`
and `domain`.

## Drafters

For Ouro and Nanbeige, train two drafters on traces generated by the W64 target:

- `w64`: features and last-loop argmax labels from exact replay of the W64 checkpoint.
- `original`: features and labels from the original model with per-loop KV.

The [drafter configs](../configs/drafter) specify the five-layer architecture, depth mix, block size,
optimizer and schedule. The pipeline is prompt pool → traces → training → export.

### 1. Build a prompt pool

```bash
python -m training.drafter.prompt_pool build --out runs/prompts-v2 \
    --benchmark-cache BENCHMARK_CACHE --benchmark-extra EXTRA.jsonl --spec-bench question.jsonl
```

To exclude prompts used for KD, create a hash list with
`python -m training.drafter.prompt_pool hash-prompts --input SHARDS/*.jsonl.gz --out kd-prompts.sha256`
and pass `--exclude-prompts kd-prompts.sha256` to `build`.

### 2. Generate traces

Trace generation runs one vLLM engine per GPU with the W64 target.

```bash
python -m training.drafter.traces launch --out runs/traces/ouro-1.4b-w64 --model ouro-1.4b-thinking \
    --variant w64 --target-path W64_CHECKPOINT --prompts runs/prompts-v2 --gpus 0 1 2 3 4 5 6 7
# After all trace workers finish:
python -m training.drafter.traces collect --out runs/traces/ouro-1.4b-w64
```

Use `status --out TRACE_DIR` to inspect progress; after an interruption,
use `requeue --out TRACE_DIR`, then `join --out TRACE_DIR --gpus ...` to restart workers.
These are subcommands of `python -m training.drafter.traces`.

### 3. Train

Each rank loads the frozen target alongside the drafter.

```bash
torchrun --standalone --nproc-per-node 8 -m training.drafter.train \
    --config configs/drafter/ouro-1.4b-thinking-w64.json --target-path W64_CHECKPOINT \
    --traces runs/traces/ouro-1.4b-w64 --out runs/drafter/ouro-1.4b-w64 --resume
torchrun --standalone --nproc-per-node 8 -m training.drafter.train \
    --config configs/drafter/ouro-1.4b-thinking-original.json \
    --traces runs/traces/ouro-1.4b-w64 --out runs/drafter/ouro-1.4b-original --resume
```

Flags override the config. For a short run in a new output directory, add
`--train-limit 512 --epochs 2 --eval-docs 16`. `--resume` continues after the last completed epoch.
Replay uses FlashAttention 3 on Hopper and FlashAttention 2 on Ampere/Ada;
`--replay-attention sdpa` selects the reference backend.

### 4. Export

```bash
python -m training.drafter.export --checkpoint runs/drafter/ouro-1.4b-w64/drafter/best.pt \
    --out runs/export/ouro-1.4b-w64 --target-path W64_CHECKPOINT --target-name ORG/W64_REPO
```

Export writes a vLLM DFlash checkpoint with the target's LM head and the learned mask embedding.
The mask token is selected automatically; `--mask-token-id` overrides it.
For a local target, `--target-name` is required to record its public identifier.

### Dory1.0-4B

Dory runs with four loops, needs no KD and uses one drafter for both targets. Its W64 target is the
base checkpoint with KV-sharing overrides; the drafter uses features and labels from Dory with per-loop KV.
Use [dory1.0-4b-w64.json](../configs/drafter/dory1.0-4b-w64.json). Dory's trace engine uses
`torch.compile`, and its target settings and export metadata are handled automatically.

```bash
python -m training.drafter.traces launch --out runs/traces/dory1.0-4b-w64 --model dory1.0-4b --variant w64 \
    --prompts runs/prompts-v2 --gpus 0 1 2 3 4 5 6 7
# After all trace workers finish:
python -m training.drafter.traces collect --out runs/traces/dory1.0-4b-w64
torchrun --standalone --nproc-per-node 8 -m training.drafter.train \
    --config configs/drafter/dory1.0-4b-w64.json --traces runs/traces/dory1.0-4b-w64 \
    --out runs/drafter/dory1.0-4b --resume
python -m training.drafter.export --checkpoint runs/drafter/dory1.0-4b/drafter/best.pt \
    --out runs/export/dory1.0-4b
```

### Drafter kind and block size

`--drafter NAME:LAYERS:DEPTH_WEIGHTS[:RECIPE]` selects the recipe: `ce-dpace` (default) trains the paper's
DFlash drafter, `dspark` a [DSpark](https://arxiv.org/abs/2607.05147) drafter with a sequential (Markov)
head and a confidence head. `--k-max` sets the block size (the given token and `K - 1` drafted ones).
Both replace the config's values:

```bash
torchrun --standalone --nproc-per-node 8 -m training.drafter.train \
    --config configs/drafter/ouro-1.4b-thinking-w64.json --target-path W64_CHECKPOINT \
    --traces runs/traces/ouro-1.4b-w64 --out runs/drafter/ouro-1.4b-w64-dspark --resume \
    --drafter "dspark:5:1=0.5,2=0.125,3=0.125,4=0.25:dspark" --save-every 500
python -m training.drafter.export --checkpoint runs/drafter/ouro-1.4b-w64-dspark/dspark/best.pt \
    --out runs/export/ouro-1.4b-w64-dspark --target-path W64_CHECKPOINT --target-name ORG/W64_REPO
```

The export records its kind, and `scripts/benchmark.py --drafter EXPORT` runs either one.
`--save-every STEPS` also writes `last.pt` inside an epoch. After an export, check that the run-time
adapter drafts what the training module drafts:

```bash
python scripts/check_drafter_export.py --model ouro-1.4b-thinking --target w64 --target-path W64_CHECKPOINT \
    --drafter runs/export/ouro-1.4b-w64-dspark --traces runs/traces/ouro-1.4b-w64/dev.jsonl
```

### Inkling 2

The fork cannot serve Inkling 2, so its traces come from the official vLLM build:
`scripts/inkling2/serve_rollout.sh` starts one OpenAI-compatible server of the checkpoint per GPU in the
vendor's image (Docker; a server answers to the registry name of its checkpoint, with the trace budget of
16,384 tokens), and one client per server works through the queue. The drafter trains on the per-loop model
with a DSpark recipe ([inkling-2-mini.json](../configs/drafter/inkling-2-mini.json),
[inkling-2-mini-varloop.json](../configs/drafter/inkling-2-mini-varloop.json)).

```bash
# On an H100 the image needs three patched files: serve_official.sh --make-hopper-patches DIR writes them,
# and --hopper-patches DIR mounts them.
for g in 0 1; do scripts/inkling2/serve_rollout.sh $g $((8100 + g)); done
python -m training.drafter.traces_remote launch --out runs/traces/inkling-2-mini --model inkling-2-mini \
    --prompts runs/prompts-v2 --servers http://127.0.0.1:8100 http://127.0.0.1:8101
python -m training.drafter.traces_remote collect --out runs/traces/inkling-2-mini
torchrun --standalone --nproc-per-node 8 -m training.drafter.train \
    --config configs/drafter/inkling-2-mini.json --traces runs/traces/inkling-2-mini \
    --out runs/drafter/inkling-2-mini --target-tensor-cores --resume
python -m training.drafter.export --checkpoint runs/drafter/inkling-2-mini/dspark/best.pt \
    --out runs/export/inkling-2-mini
```

`--target-tensor-cores` runs the frozen target about four times faster on an H100; an 80 GB card needs
`--micro-blocks 128` with it. For the variable-loop checkpoint pass `--repo` and `--revision` of
`configs/models.json` to `serve_rollout.sh` (its server then answers to `inkling-2-mini-varloop`),
`--model inkling-2-mini-varloop` to `traces_remote launch` and
`--config configs/drafter/inkling-2-mini-varloop.json` to the trainer.
